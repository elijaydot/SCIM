# Source IP Anchoring (SIPA)

Source IP Anchoring is a networking and Zero Trust access technique that ensures specific application traffic always exits through a known, dedicated public IP address instead of a dynamic cloud or user IP address. This allows applications to enforce IP-based access controls and trust connections coming from approved corporate networks.

**Why is it needed?**
Many SaaS and legacy applications only allow access from pre-approved IP addresses.

Without Source IP Anchoring:
```text
User → SSE/Proxy → Internet
              ↓
        Dynamic Egress IP
```

The destination application sees varying source IPs, making IP allowlisting difficult.

With Source IP Anchoring:
```text
User
  ↓
Global Secure Access / Zscaler
  ↓
Private Network Connector
  ↓
Corporate Network/NAT
  ↓
Application

Application sees:
203.x.x.x (Corporate Public IP)
```

The application always sees the same trusted corporate IP address.

**Microsoft Global Secure Access Example**
In Microsoft Entra Private Access, Source IP Anchoring tunnels traffic through:
    - User device
    - Microsoft Secure Service Edge
    - Private Network Connector
    - Corporate network
    - Internet application

The destination application sees the organization's approved egress IP and grants access based on its IP policy.

Common Use Cases
    - SaaS applications with IP allowlisting
    - Third-party vendor portals
    - Banking and financial systems
    - Legacy web applications
    - Conditional Access policies requiring trusted network locations
    - Applications that do not support modern identity authentication

Source IP Anchoring vs Source IP Restoration
Feature	                Purpose
Source IP Anchoring	    Makes the application see a trusted corporate IP address.
Source IP Restoration	Preserves and records the user's original public IP for logging, auditing, and Conditional Access.

Microsoft explicitly notes that these are different features serving different purposes.

**Interview Definition**    
    Source IP Anchoring is a method of routing selected application traffic through a designated corporate egress point so that the destination application always sees a predefined, trusted public IP address, enabling IP-based access control and allowlisting.

For your Global Secure Access (GSA) studies, think of Source IP Anchoring as:

**"Making cloud application traffic appear as if it originated from the corporate office network."**

**Question**
for this Source IP anchoring, how & where  are the IPs of the different users/devices tracked for Audit purpose since everyone is definitely going to have different IP addresses.

**Answer**
Great question. Source IP Anchoring does not eliminate visibility of individual users. It only changes the IP address that the target application sees.

Think of it like a company office:
    - 500 employees access the internet.
    - The internet sees only the company's public NAT IP (for example, 52.x.x.x).
    - Internally, the company still knows which employee (10.10.1.25) generated the traffic.

The same principle applies to Source IP Anchoring.

**What the Application Sees**

The SaaS application sees:
```text
User A → 15.4.23.54
User B → 15.4.23.54
User C → 15.4.23.54
```

All traffic appears to originate from the anchored corporate IP. This is the entire purpose of Source IP Anchoring.

**Where User Identity Is Actually Tracked**
The individual user/device information is logged by the components that handled the connection before it reached the anchored IP.

For example, in Microsoft Entra Global Secure Access:
```text
User Device
   ↓
GSA Client
   ↓
Microsoft Secure Service Edge
   ↓
Private Network Connector
   ↓
Corporate Egress IP
   ↓
Application
```

Audit data can be captured at:
1. Global Secure Access Client
    - ogged-in user
    - Device ID
    - Device compliance state
    - User session

2. Microsoft Entra ID Sign-in Logs
    - User account
    - Device details
    - Authentication method
    - Location information

3. Private Network Connector Logs
    - Which user session was mapped to which application request

4. SIEM (Microsoft Sentinel, Splunk, etc.)
    - Correlation of user, device, session and application access events

Source IP Anchoring affects the application's view of the source IP, not these audit records.

**What About the User's Original Public IP?**
This is where Source IP Restoration comes in.

Microsoft specifically distinguishes Source IP Anchoring from Source IP Restoration. Source IP Restoration securely communicates the user's original egress IP to Microsoft Entra so that sign-in logs, Conditional Access, risk detections, and audit records can still reflect the user's true source IP rather than only the proxy's IP.

Example:
```text
User Home ISP IP:
102.45.20.15

Anchored Corporate IP:
15.4.23.54
```

Result:

System	                                            IP Seen
SaaS Application	                                15.4.23.54
Entra Sign-in Logs (with Source IP Restoration)	    102.45.20.15
GSA Audit Logs	                                    102.45.20.15 + User Identity
SIEM	                                            Both values can be correlated

**Real-world Audit Example**
Suppose:
    - User: john@contoso.com
    - Device: LAPTOP-001
    - Home IP: 102.45.20.15
    - Anchored IP: 15.4.23.54

The SaaS application log may show:
```text
User authenticated from IP 15.4.23.54
```

But Entra/GSA logs can show:
```text
User: john@contoso.com
Device: LAPTOP-001
Original IP: 102.45.20.15
Anchored IP Used: 15.4.23.54
Application: Salesforce
Time: 09:30 UTC
```

This gives security teams full attribution while still satisfying the application's IP allow-list requirements.

**Interview Answer**
    Source IP Anchoring only changes the source IP presented to the destination application. User-level auditing is maintained through Microsoft Entra sign-in logs, Global Secure Access logs, endpoint identity, and optionally Source IP Restoration, which preserves the user's original public IP for auditing and Conditional Access purposes. The application sees the anchored IP, while security administrators can still trace activity back to the individual user and device.

# DEVICE ID VS OBJECT ID
In Microsoft Entra ID / Azure AD, Device ID and Object ID are often confused because they're usually the same value for a device object, but they serve different conceptual purposes.

**Device ID**
- A Device ID uniquely identifies a device registration in Microsoft Entra.
- It's generated when a device is:
    - Azure AD Joined
    - Hybrid Azure AD Joined
    - Azure AD Registered
- Used primarily by device authentication and device management services.
- You can see it via:
```text
dsregcmd /status
```

Output:

```text
Device Details
--------------
DeviceId : a1b2c3d4-e5f6-1234-5678-abcdef123456
```

**Object ID**
- An Object ID is the unique identifier of any object stored in Microsoft Entra.
- Every object has one:
    - User
    - Group
    - Application
    - Service Principal
    - Device

Examples:
```text
User Object ID
Group Object ID
Device Object ID
Application Object ID
```

Microsoft Entra uses the Object ID as the primary key for directory objects.

## For Device Objects

When you open a device in Entra Admin Center:

Identity
 └─ Device Object
      ├─ Device ID
      └─ Object ID


You'll often find:

Device ID = a1b2c3d4-e5f6-1234-5678-abcdef123456
Object ID = 9f8e7d6c-1111-2222-3333-444455556666


In this case:
    - Device ID = Identity used by the device itself.
    - Object ID = Identity of the device record in the directory.

They are usually different GUIDs.

## Real-World Example
Suppose Elijah's laptop is registered in Entra.
```text
Device Name : ELIJAH-LT01

Device ID :
a1b2c3d4-e5f6-1234-5678-abcdef123456

Object ID :
9f8e7d6c-1111-2222-3333-444455556666
```

## Authentication Process
```text
Device
  |
  | Uses Device ID
  v
Microsoft Entra

Entra Directory
  |
  | Stores device as an object
  v
Object ID
```


The device presents its Device ID during device authentication, while administrators, Graph API, Conditional Access, and directory operations typically reference the Object ID.

## Where You See Each
Device ID
```text
dsregcmd /status
```

```powershell
Get-MgDevice
```

Used for:
    - Device registration
    - Device certificates
    - PRT (Primary Refresh Token) associations
    - Device authentication

## Object ID

Used for:
    - Microsoft Graph queries
    - Entra administration
    - Conditional Access targeting
    - Directory lookups
    - Audit logs

**Interview Answer**
    Device ID identifies the physical/logical device during device registration and authentication, whereas Object ID identifies the device object stored in Microsoft Entra ID. Device ID is used by the device itself, while Object ID is used by the directory and administrators to manage and reference that device.

# IP Mismatch
IP Mismatch occurs when the IP address used during an authenticated session changes unexpectedly.

Example:
```text
1. User signs in from:
   102.45.20.15

2. A few minutes later, requests come from:
   41.74.10.22
```

Security systems may interpret this as:
    - Session hijacking
    - Token theft
    - VPN change
    - User moving between networks (Wi-Fi → Mobile hotspot)
    - Proxy/SSE routing change

# IP Mismatch in Conditional Access (CA)
In Microsoft Entra ID Conditional Access, IP Mismatch generally means the IP evaluated by the policy does not match the trusted, expected, or previously known IP.

Common scenarios:
**Scenario 1: Named Location Mismatch**

CA Policy:
```text
Allow access only from:
196.12.50.0/24
```

User signs in from:
```text
102.45.20.15
```

Result:
```text
CA Policy Failure
Reason: IP Address Not In Named Location
```

**Scenario 2: Source IP Anchoring + No Source IP Restoration**

Consider:
```text
Real User IP:
102.45.20.15

Anchored IP:
15.4.23.54
```

Application sees:
```text
15.4.23.54
```

But Conditional Access might evaluate:
```text
102.45.20.15
```

or
```text
15.4.23.54
```

depending on the configuration and whether **Source IP Restoration** is enabled in Microsoft Entra Global Secure Access. Microsoft distinguishes Source IP Restoration from Source IP Anchoring because Restoration allows the original client IP to be preserved for logging and Conditional Access evaluation.

This can lead to administrators seeing what appears to be an "IP mismatch."

**Scenario 3: Token Theft Detection**

A sign-in might occur from:
```text
Kigali:
102.45.20.15
```

Then shortly after from:
```text
London:
51.x.x.x
```

Microsoft Entra ID Protection may flag:
```text
Atypical Travel
Unfamiliar Sign-in
Risky Sign-in
```

because the IP information is inconsistent with normal user behavior.

# How to Identify IP Mismatch in Logs

Check:

Entra Admin Center
```text
Identity
 └─ Monitoring & Health
     └─ Sign-in Logs
```

Review:
    - IP Address
    - Network Location
    - Conditional Access tab
    - CA Failure Reason
    - Authentication Details

Common messages:
```text
Failure:
Access blocked by Conditional Access

Reason:
Not from trusted network
```

or
```text
Grant Controls Not Satisfied
```

**Interview Answer**
    An IP mismatch occurs when the source IP associated with a user session differs from the IP expected by security controls or from earlier authentication activity. In Conditional Access, this commonly happens when a user's IP is not part of a trusted named location, when VPN/proxy routing changes the apparent source IP, or when technologies such as Source IP Anchoring and Source IP Restoration affect which IP is evaluated. The result can be Conditional Access policy failures, additional MFA prompts, or risk detections.

**Quick Troubleshooting Checklist**
When you see a CA failure due to IP mismatch:
    1. Verify the IP in the Sign-in Logs.
    2. Check the Conditional Access policy's Named Locations.
    3. Confirm whether a VPN, Proxy, Zscaler, or Global Secure Access service is in use.
    4. Determine whether Source IP Restoration is enabled.
    5. Compare:
        - User's real IP
        - Egress/Anchored IP
        - IP evaluated by CA
    6. Review the Conditional Access tab in the sign-in log for the exact policy result.
