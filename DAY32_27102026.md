What is Web Application Proxy?
 
Web Application Proxy is a role service of the Remote Access server role starting in Windows Server® 2012 R2. Web Application Proxy provides reverse proxy functionality for web applications inside your corporate network to allow users on any device to access your web applications from outside the corporate network.
 
It combines the AD FS Proxy and a web publishing service (proxy to publish apps):
 
Should be located in the DMZ / Edge Network.
AD FS & the Web Application Proxy provides services for authentication, authorization, and access to applications located inside the corporate network from outside the corporate network.
It tags authentication requests as coming from outside the LAN.

Collect and analyze ADFS Tracing/Debug event logs
 
 
The AD FS Debug log is where detailed messages are logged and will be the most useful log when troubleshooting. With these logs, you might have deeper information for each AD FS Admin log. Since a lot of trace log information can be generated in a short amount of time, which can impact system performance, the trace logs are disabled by default.

After collecting the logs in the following lesson, copy them to a machine with AD FS role installed and start your investigation. When investigating, try to identify the affected user to facilitate the investigation. After reproducing the issue while the Debug log is enabled, please disable it to avoid performance issues on the AD FS server.
 
 
Collect and analyze AD FS Admin Event Logs
 
 
The Admin log provides high level information on issues that are occurring and is enabled by default. You may use these logs to help you investigate possible issues occurring in the federation server.

Update SSL certificate settings
In case the certificates don’t match, you have three options:
1. Update SSL certificate using Azure AD Connect:
Microsoft Entra Connect - Update the TLS/SSL certificate for an AD FS farm - Microsoft Entra ID | Mi…
    In case the Customer uses Azure AD Connect, use it to update the SSL certificate on the impacted AD FS and WAP servers. Follow the instructions at Update the SSL certificate for an Active Directory Federation Services (AD FS) farm.
 
2. Update SSL certificate manually:
    Update the SSL bindings manually for the ADFS and WAP servers:
    Example:  If the thumbprint of the SSL cert is 3638de9b03a488341dfe32fc3ae5c480ee687793
 
    1. For AD FS Server Nodes, use 
        "Set-AdfsSslCertificate -Thumbprint 3638de9b03a488341dfe32fc3ae5c480ee687793".
    2. For WAP Servers, 
        "Set-WebApplicationProxySslCertificate -Thumbprint 3638de9b03a488341dfe32fc3ae5c480ee687793".
    3. If IP Port bindings for 0.0.0.0:443 are present, run the following:
        Run "netsh http delete sslcert ipport=0.0.0.0:443"
        Run "netsh http add sslcert ipport=0.0.0.0:443 certhash=<ssl cert thumbprint> appid='{5d89a20c-beab-4389-9447-324788eb944a}' sslctlstorename=AdfsTrustedDevices"
 
3. Update SSL certificates manually using netsh:
    Mixed mode AD FS farms are meant to be a transitionary state. It is recommended during your planning to either roll over the SSL certificate prior to the upgrade process or complete the process and increase the farm behavior level prior to updating the SSL certificate. 
    When AD FS farms are in Mixed mode, changing the SSL certificate using PowerShell will not be allowed. To overcome this limitation, use netsh following the steps as given below:
    1. Select subset of ADFS 2016 servers for maintenance (e.g., remove from load balancer).
    2. On the servers selected in #1, import the new certificate via MMC.
    3. Delete the existing certificates:
        netsh http delete sslcert hostnameport=fs.contoso.com:443
        netsh http delete sslcert hostnameport=localhost:443
        netsh http delete sslcert hostnameport=fs.contoso.com:49443
 
    4. Add the new certificate:
        netsh http add sslcert hostnameport=fs.contoso.com:443 certhash=THUMBPRINT appid="{5d89a20c-beab-4389-9447-324788eb944a}" certstorename=My verifyclientcertrevocation=Enable sslctlstorename=AdfsTrustedDevices
        netsh http add sslcert hostnameport=localhost:443 certhash=THUMBPRINT appid="{5d89a20c-beab-4389-9447-324788eb944a}" certstorename=My verifyclientcertrevocation=Enable
        netsh http add sslcert hostnameport=fs.contoso.com:49443 certhash=THUMBPRINT appid="{5d89a20c-beab-4389-9447-324788eb944a}" certstorename=My verifyclientcertrevocation=Enable clientcertnegotiation=Enable
 
    5. For 0.0.0.0:443, delete and recreate run the following:
        netsh http delete sslcert ipport=0.0.0.0:443
        netsh http add sslcert ipport=0.0.0.0:443 certhash=<ssl cert thumbprint> appid="{5d89a20c-beab-4389-9447-324788eb944a}" sslctlstorename=AdfsTrustedDevices
    6. Restart ADFS service on the selected server.
    7. Remove subset of WAP servers for maintenance.
    8. On the selected WAP servers, import the new certificate via MMC.
    9. Set the new cert on WAP using cmdlet.
    10. Set-WebApplicationProxySslCertificate -Thumbprint "CERTTHUMBPRINT".
    11. Restart service on the selected WAP servers.
    12. Put the selected WAP and AD FS servers back in production environment.
 
Command to Check existence of self-signed certificates
    Run the following PowerShell command on all ADFS and WAP servers to make sure that there are no non-self-signed certificates in the trusted root cert store:
        Get-Childitem cert:\LocalMachine\root -Recurse | Where-Object {$_.Issuer -ne $_.Subject} | Format-List * | Out-File "c:\CARootNonSelfSignedCerts.txt" 
        notepad c:\CARootNonSelfSignedCerts.txt
 
    If there are any non-self-signed certificates in the trusted root cert store move them to the intermediate store if they exist following steps below:
        Open certlm.msc.
        Go to Certificates (Local Computer) > Trusted Root Certification Authorities > Certificates.
        Locate the certificate(s) from c:\CARootNonSelfSignedCerts.txt.
        Right select on the certificate.
        Select Cut.
        Go to Certificates (Local Computer) > Intermediate Certification Authorities > Certificates.
        Right select on Certificates.
        Select Paste.

Enabling Strong Authentication for .NET applications
    The .NET Framework 3.5/4.0/4.5.x applications can switch the default protocol to TLS 1.2 by enabling the SchUseStrongCrypto registry key. This registry key will force .NET applications to use TLS 1.2. 
    Starting with AD FS on Windows Server 2016 and Windows Server 2012 R2 you need to use the .NET Framework 4.0/4.5.x key: HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\.NETFramework\v4.0.30319
 
For the .NET Framework 3.5 used when pure AD FS 2012, use the following command:
    New-ItemProperty -path 'HKLM:\SOFTWARE\Wow6432Node\Microsoft\.NETFramework\v2.0.50727' -name 'SchUseStrongCrypto' -value '1' -PropertyType 'DWord' -Force | Out-Null
    Note: AD FS version pure 2012 uses .NET Framework 3.5 and is not supported by Microsoft. 
    For the .NET Framework 4.0/4.5.x use the following command:
    New-ItemProperty -path 'HKLM:\SOFTWARE\Microsoft\.NetFramework\v4.0.30319' -name 'SchUseStrongCrypto' -value '1' -PropertyType 'DWord' -Force | Out-Null
 
 
Investigating TLS version
Follow steps below to investigate which TLS version is used by the client to establish the TLS handshake.
 
Step 1:
    Collect a network trace using AD FS tracing or install network trace on WAP server. 
    Reproduce the issue. 
    Use filter TLS to check the TLS handshake between client (WAP) and server (AD FS).
    Expand TLS parameter and check which TLS version is used by WAP server.
 
Step 2:
Run the commands explained in step 24. Check TLS version between AD FS and WAP servers on AD FS servers to identify if the respective TLS version is enabled.
Example: As TLS 1.0 is used by WAP server when facing the issue, run commands below to check if TLS 1.0 is Enabled on AD FS server.
 
    Get-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Client' | Select Enabled,DisabledByDefault 
    Get-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Server' | Select Enabled,DisabledByDefault
 
Cause:
    Many customers are considering the option to disable TLS 1.0 and RC4 protocol on AD FS, and replace it with TLS 1.1 or a later version.
 
Fix:
    If customer disabled TLS 1.0 and older versions in AD FS, guarantee that all WAP and AD FS servers use the latest TLS version following steps below.
 
Step 1:
Enable TLS 1.2 on WAP servers running commands below:
    New-Item 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.2\Server' -Force | Out-Null
    New-ItemProperty -path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.2\Server' -name 'Enabled' -value '1' -PropertyType 'DWord' -Force | Out-Null
    New-ItemProperty -path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.2\Server' -name 'DisabledByDefault' -value 0 -PropertyType 'DWord' -Force | Out-Null
    New-Item 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.2\Client' -Force | Out-Null
    New-ItemProperty -path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.2\Client' -name 'Enabled' -value '1' -PropertyType 'DWord' -Force | Out-Null
    New-ItemProperty -path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.2\Client' -name 'DisabledByDefault' -value 0 -PropertyType 'DWord' -Force | Out-Null
 
Follow Enabling Strong Authentication for .NET applications instructions in this document to force WAP use most recent TLS version.
    Restart all servers that had the TLS registry keys updated to take effect.
    Run command Install-WebApplicationProxy again to re-establish the trust between WAP and AD FS:
    Check event 245 on AD FS Admin logs on WAP server: The federation server proxy successfully retrieved and updated its configuration from the Federation Service 'federation service name'.
 
Confirming WAP TLS version with network trace
    With TLS 1.2 configured as preferred method on WAP servers, we notice the TLS handshake completed successfully and confirm that WAP is now using TLS 1.2 on Network trace.

Reset WAP trust
 
Once all configurations are verified, reset the WAP trust using the Install-WebApplicationProxy PowerShell cmdlet.
 
Example: If the thumbprint of the SSL cert is 3638de9b03a488341dfe32fc3ae5c480ee687793 and the federation service name is fs.contoso.com
 
Notes: The account used for establishing the trust needs to have administrator rights on the AD FS servers. Don’t rely on the AD FS service account because it doesn’t require local admin rights. If there is a Load Balancer or Firewall that does SSL offloading, then it’s not a supported configuration.
 
Run all commands from elevated PowerShell:
    Install-WebApplicationProxy -FederationServiceName fs.contoso.com -CertificateThumbprint "3638de9b03a488341dfe32fc3ae5c480ee687793"
